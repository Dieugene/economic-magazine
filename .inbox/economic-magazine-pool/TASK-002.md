## Контекст

При сохранении статьи (POST `/api/articles/`) с непустым `references.en` и пустым `references.ru` бэк отвечает 400. В обоих сессиях 2026-05-10 и 2026-05-11 проверено: фронт показывает toast.error с заголовком «Не удалось сохранить статью» — поведение корректное, ложно-позитивного «Статья создана» нет (Bug-6 закрыт).

Однако содержимое toast — сырой Python-репр объекта DRF:

```
{'references': [ErrorDetail(string='Значение в ключе ru: значение должно быть непустой строкой.', code='invalid')]}
```

Эталонное содержание ошибки, которое реально нужно показать пользователю (содержится в `string=...`):

```
Значение в ключе ru: значение должно быть непустой строкой.
```

Опционально можно добавить контекст поля:

```
Литература (RU): значение должно быть непустой строкой.
```

## Жёсткое доказательство (QA-сессия 2026-05-11)

Воспроизведено в строке Coverage Log `Toast-UX` сессии `2026-05-11-staging-v0.1.11-strict.md`. См. также раздел «Notes / observations / Obs-1» того же отчёта.

## Запрос / Постановка

В `parseApiError` (`02_src/vte-frontend/src/lib/api/errors.ts`) добавить ветку, которая распознаёт DRF-формат «массив строк под именованным ключом словаря» и вытаскивает читаемое сообщение. Сейчас, видимо, ветка падает в `JSON.stringify`/`toString`, возвращая Python-`repr` (что говорит о том, что бэк прислал тело именно в таком виде — но даже так строка `ErrorDetail(string='...')` парсится регулярным выражением, либо ловится на этапе JSON-парсинга самого ответа).

Желаемое поведение: если 400-ответ имеет форму `{ <field>: [<message:string>, ...] }` либо `{ <field>: [{ string: <message> }] }` либо `{ <field>: "<message>" }` — вытащить первое сообщение, форматировать как «<человечное имя поля>: <message>». Mapping имён полей (`references` → «Литература», `title` → «Заглавие» и т.д.) может уже существовать в проекте — переиспользовать его.

Запас прочности: если форма ответа неизвестная — текущий fallback (`JSON.stringify` / `toString`) сохранить, но обернуть строкой `«Не удалось сохранить статью: <fallback>»` (или просто оставить как есть — это не регрессия).

## Acceptance / Критерии готовности

- [ ] Создание статьи с пустым `references.ru` и непустым `references.en` показывает toast.error с человечным текстом, без `ErrorDetail(string=...)` и без фигурных Python-скобок.
- [ ] Аналогично для других полей с условной обязательностью (`abstract.en`, `funding.en`, `title.en` и др.) — если их валидация на бэке выдаёт похожий формат, фронт показывает читаемое сообщение.
- [ ] Регрессия не появилась: HTTP 200 / OK всё ещё показывает success-toast «Статья создана» / «Статья сохранена»; неизвестные форматы ошибок продолжают показывать что-то (не пустой toast).
