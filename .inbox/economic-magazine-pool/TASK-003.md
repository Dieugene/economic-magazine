# TASK-003: Obs-2 — Inline-error для маски даты при aria-invalid

**От:** qa
**Кому:** dev
**Дата:** 2026-05-11
**Связанные задачи:** —
**Файлы кода (вероятные точки):** `02_src/vte-frontend/src/components/admin/DateInput.tsx`, `02_src/vte-frontend/src/lib/utils/date.ts`.
**Severity:** S4 / nit. Реальный пользователь без DevTools этот путь практически не воспроизводит (маска ввода фильтрует посимвольно), но желательно закрыть.

## Контекст

Поле «Дата выхода» в форме выпуска (`/control/issues/{id}/` блок «ДАННЫЕ НОМЕРА») использует маску `ДД.ММ.ГГГГ`. В этой версии (v0.1.11) маска корректно отвергает невалидные значения при имитации клавиатуры:

- На форме issue#12 (текущее значение `01.06.2026`) попытка ввести `32.13.2026` через посимвольную имитацию ввода (MCP `fill`) **отбрасывается** — поле остаётся `01.06.2026`. Сохранение проходит с прежним валидным значением. Toast «Выпуск сохранён». Это улучшение по сравнению с прошлой сессией.

Однако через программный bypass (например, в paste-сценариях или некоторых клиентских скриптах):

```js
const setter = Object.getOwnPropertyDescriptor(HTMLInputElement.prototype, 'value').set;
setter.call(input, '32.13.2026');
input.dispatchEvent(new Event('input', { bubbles: true }));
```

— фронт принимает строку `32.13.2026` в поле. Видим:
- `input.value === '32.13.2026'`,
- `input.getAttribute('aria-invalid') === 'true'`.

Но визуально ничего не происходит: нет красной подсветки, нет inline-text ошибки рядом с полем (есть только подпись «Формат: ДД.ММ.ГГГГ» — она не меняется).

Если такой же путь срабатывает при вставке из буфера обмена через `Ctrl+V` (тоже idет через input-event), пользователь визуально получит поле, выглядящее «нормально» (значение в нем стоит), но логически невалидное — сохранение либо отвергнется бэком, либо запишет невалидную дату, в зависимости от текущей валидации.

## Запрос / Постановка

Когда поле получило `aria-invalid="true"` (т.е. внутренняя валидация даты сказала «значение не разбирается в валидную ISO-дату»):

1. Добавить визуальную подсветку: цвет рамки или текста, какой принят в проекте для невалидных полей (надо посмотреть существующие паттерны — возможно уже есть `data-invalid` класс / CSS).
2. Под полем (или внутри `aria-describedby` рядом) — короткое сообщение: «Неверная дата» (RU) / «Invalid date» (EN). Можно через next-intl, ключ `forms.dateInvalid` или эквивалент.
3. Если кнопка «Сохранить данные» отправляет PATCH с невалидным значением в `published_date` — этого делать не надо. Желательно блокировать submit при `aria-invalid="true"`. Альтернатива — отправить, бэк ответит 400, и пользователь поймёт по toast (но это уже текущее поведение, см. TASK-002 про DRF-ошибки в toast).

Реализация — на усмотрение разработчика. Чисто UX-задача, без бэка.
