# TASK-004: Bug-B regression guard — комментарий в коде формы статьи

**От:** qa
**Кому:** dev
**Дата:** 2026-05-11
**Связанные задачи:** —
**Файлы кода (вероятные точки):** `02_src/vte-frontend/src/app/(control)/control/articles/[id]/page.tsx` (или модуль с `handleSave` / `handleUploadPdf` формы статьи).
**Severity:** S5 / guard (не баг, а защита от будущей регрессии).

## Контекст

В QA-сессии 2026-05-10 был зафиксирован **Bug-B**: кнопка «Сохранить изменения» в форме статьи делала PATCH полей + POST upload PDF из одного handler'а; при не-PDF файле upload отвечал 400, а фронт показывал только зелёный toast «Статья сохранена», скрывая ошибку. Подробности — `00_docs/qa/sessions/2026-05-10-staging-v0.1.11.md` раздел Bug-B.

В сессии 2026-05-11 этот путь не воспроизводится: UI разнёс «Загрузить PDF» и «Сохранить изменения» в **отдельные handler'ы с одним запросом каждый** — см. `00_docs/qa/sessions/2026-05-11-staging-v0.1.11-strict.md` строки Coverage Log `F6`, `8.7`, `Bug-B`. Поэтому в новой регрессии QA пометил Bug-B как `N/A by design`.

**Класс бага закрыт архитектурой UI, не валидацией.** Если через 3 месяца кто-то решит «сделать один общий save для удобства UX» и снова соединит upload с PATCH в одном клике без явной обработки 400 от upload — Bug-B вернётся, причём никаких автоматических тестов на UI у проекта нет, и регрессия будет замечена только при следующем ручном прогоне.

QA-страховка уже добавлена: новый кейс §7.8 в тест-плане `00_docs/qa/test_plan_issues_sections_articles.md` (см. коммит этой же даты). Этот тикет — парная мера в коде.

## Запрос / Постановка

Добавить **однострочный код-комментарий** рядом с handler'ами формы статьи (любой из вариантов: над функцией save, над функцией upload, в JSX рядом с кнопками, или в нескольких местах сразу — на твоё усмотрение). Текст комментария:

```
// Bug-B (2026-05-10): не объединять save (PATCH полей) и upload PDF в один handler без явной обработки 400 от upload. См. test_plan §7.8.
```

или короче, если стиль кода требует:

```
// Bug-B guard: save и upload PDF — раздельные handlers. См. test_plan §7.8.
```

Текст и точное место — на твой вкус. Главное — чтобы при будущей правке формы статьи разработчик увидел маркер «здесь нельзя склеивать» при чтении кода.

## Что НЕ нужно делать

- **Не нужно** добавлять валидацию PDF на фронте — она уже есть на бэке и работает (см. §F6, §8.7 в тест-плане).
- **Не нужно** делать рефакторинг handler'ов или менять их сигнатуры. Только комментарий.
- **Не нужно** трогать формы выпуска (`/control/issues/{id}/`) — там та же архитектура: «Сохранить данные» и «Выбрать PDF-файл» — раздельные кнопки. Если у тебя есть однострочный аппетит — можешь и там добавить такой же маркер.
