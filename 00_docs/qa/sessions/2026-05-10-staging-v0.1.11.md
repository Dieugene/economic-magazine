## Charter (миссия сессии)

Прогнать полный регрессионный план `test_plan_issues_sections_articles.md` против фактически задеплоенного релиза v0.1.11 на staging-стенде заказчика (не localhost). Цель — подтвердить готовность релиза с точки зрения комплексной связки Выпуски ↔ Рубрики ↔ Статьи + публичные статичные страницы + UX-уведомления; выявить регрессии и новые дефекты; зафиксировать состояние staging-стенда для дальнейших сессий.

## Scope

**Включено:**

- Smoke S1–S6
- Functional F1–F12 (с оговорками по `published_date`, см. ниже)
- CRUD E1–E4
- Регрессии 7.1–7.7
- Edge 8.1–8.7
- §9.1–9.6 публичные статичные страницы и UX
- Очистка по §10 (с учётом политики staging — не подчищать «носители регрессии»)

**Исключено явно:**

- **Кейсы редактирования поля «Дата выпуска» через PATCH** (часть §F10a, §F8a-метаданные про дату, строка `Дата выпуска` в §E1). По продуктовому решению от 2026-05-10 (заказчик): редактирование `published_date` после создания номера не требуется; бэкендер не реализует PATCH-обработку поля. POST-сохранение даты при создании выпуска — продолжаем тестировать. Если фронт «принимает» правку и шлёт PATCH, который бэк молча игнорирует — фиксируем как **N/A**, не как FAIL.
- **§F2 шаг 1** (искусственная отписка рубрик через curl) — пропускаем, если автоподписка работает в §F1; провоцируем только при FAIL §F1.

**Эмпирическая преамбула (диагностика, разрешена §7.1):**

- Login + POST /issues/ с `published_date` + PATCH с другой датой + GET → `published_date` после PATCH остался прежним. POST принимает корректно. Подтверждает текущее поведение бэка по `published_date`.

## Найденные баги

> Критических и серьёзных дефектов в рамках scope не найдено. Все наблюдения — UX-nit'ы и контрактные нюансы, ниже по убыванию важности.

### Obs-1. Пустая аннотация → пустой heading «Аннотация» на публичной странице

- **Severity:** S4 (косметика)
- **Затронутый компонент:** публичная страница статьи `/article/{id}/` (рендеринг `ArticleView`)
- **Воспроизведение:**
  1. Открыть `/article/8/` (QA-A4) или `/article/9/` (QA-A5) — у обеих статей `abstract.ru = ""`, `abstract.en = ""`.
  2. Найти заголовок «Аннотация».
- **Ожидаемое:** если оба `abstract.ru/en` пустые, либо скрыть весь блок «Аннотация», либо показать заглушку.
- **Фактическое:** заголовок «Аннотация» рендерится без текста, далее сразу идёт блок «Ключевые слова». Визуально выглядит как недоработка вёрстки.
- **Доказательства:** `evaluate_script` `abstract.parentElement.outerHTML` — между `<h3>Аннотация</h3>` и блоком keywords нет ни `<p>`, ни заглушки.
- **Зарегистрирован:** не блокирует, не зарегистрирован отдельным таском. Можно закрыть в следующей минорной правке: `if (!abstract.ru && !abstract.en) return null;` либо «Аннотация недоступна».

### Obs-2. PATCH `published_date` молча игнорируется бэком

- **Severity:** N/A (продуктовое решение)
- **Затронутый компонент:** API бэк-сервиса
- **Воспроизведение:** POST `/api/issues/` с `published_date: "2026-04-01"` → сохраняется. Затем PATCH `/api/issues/{id}/` с `published_date: "2026-09-15"` → ответ возвращает `2026-04-01`, GET подтверждает: дата не изменилась.
- **Ожидаемое:** либо PATCH принимает поле, либо возвращает 4xx/предупреждение.
- **Фактическое:** молчаливое игнорирование (Swagger описывает поле, но handler не обрабатывает).
- **Зафиксировано:** заказчик и бэкендер согласовали, что редактирование даты после создания не требуется. Решение — оставить как есть; при необходимости в будущем можно отключить поле даты в форме редактирования (Edit-mode), сохранив его только в Create-mode, чтобы не вводить редактора в заблуждение. **Не FAIL по текущему scope.**

### Obs-3. References: фронт-валидация при заполненном RU и пустом EN

- **Severity:** S4 (контрактный нюанс)
- **Затронутый компонент:** контракт между фронтом и бэком на `references`
- **Воспроизведение:** POST статьи с `references: [{ru: "Источник 1.", en: ""}]` → бэк возвращает HTTP 400 «Ошибка со значением данных».
- **Ожидаемое:** бэк или принимает массив с пустой одной из локализаций, или фронт-форма не позволяет сохранить такое состояние.
- **Фактическое:** фронт-форма уже предусматривает валидацию (звёздочка обязательности EN при заполненной RU), бэк отвергает в крайнем случае. Текст ошибки бэка пользователю показывается через всплывашку.
- **Не FAIL.** Поведение согласованное.

## Резюме для заказчика (понятным языком)

**Что проверяли:** работу журнала «Вопросы теоретической экономики» в опубликованной версии 0.1.11, целиком, по всему сценарию редактирования и публичного представления — на боевом тестовом стенде `http://185.180.230.243/`.

**Что охватили:**

- Список номеров и редактирование каждого (черновик, готов, опубликован);
- Все три перехода статусов в обе стороны (черновик → готов → опубликован → обратно в черновик);
- Создание нового номера, проверка защиты от дубликатов (год + номер);
- Привязку рубрик: при создании номера все рубрики справочника автоматически отмечены, рубрикатор удалён из меню админки;
- Сортировку статей по диапазону страниц — и в форме номера, и на публичной странице;
- Запрет публикации без PDF выпуска и без PDF каждой статьи — кнопка «Опубликовать» блокируется и подсказывает редактору причину;
- Соответствие предпросмотра статьи и публичной страницы — на статье с большой аннотацией (5 445 символов) аннотация выводится полностью, без обрезки;
- Стабильность повторного открытия предпросмотра — блок «Для цитирования» рендерится корректно;
- Двуязычность RU/EN на всех публичных страницах: заголовки, меню, footer, sidebar, текст cookie-уведомления и страницы политики;
- Публичные статичные страницы: «Авторам» с четырьмя подразделами (Подать статью, Порядок подачи и оформления, Авторское соглашение, Порядок рецензирования), «Этика», «Политика обработки персональных данных» (RU + английская заглушка с обещанием перевода);
- Cookie-уведомление при первом заходе и его поведение после согласия / при удалении согласия;
- Проверку email — везде используется только адрес `editorqet@inecon.ru`;
- Систему всплывающих уведомлений — успех / ошибка / предупреждение появляются при каждом действии редактора;
- Регрессию по утечке статей-черновиков на публичные страницы (была критическая, ранее закрыта на бэке) — не воспроизводится.

**Что работает корректно:**

- Все основные действия редактора в админке: создание, редактирование, удаление номеров и статей; переходы статусов; загрузка PDF; назначение рубрик.
- Изменения в опубликованном номере и его статьях сразу попадают на публичную часть после сохранения.
- Превентивная блокировка кнопки публикации с подсказкой, чего именно не хватает (PDF выпуска или конкретная статья без PDF).
- Защита от создания дубликата номера: при попытке завести «2026 № 92», когда такой уже есть, система показывает понятное сообщение и не отправляет запрос на сервер.
- Двуязычные публичные страницы и переключение RU/EN.
- Уведомление об использовании cookie с корректными текстами на обоих языках, кнопками «Согласен» / «Не согласен» и редиректом при отказе.
- Правильное отображение даты выпуска в формате ДД.ММ.ГГГГ и поля ввода с маской на форме номера.

**Что замечено (некритично, на доработку «когда дойдут руки»):**

1. На публичной странице статьи, у которой не заполнена аннотация (например, на статьях из выпуска №92), показывается заголовок «Аннотация» без текста под ним. Если оба языка пустые, заголовок лучше скрывать целиком или ставить заглушку.

2. Поле «Дата выхода» в форме уже опубликованного номера формально доступно для редактирования, но изменение не сохраняется (бэкенд не перепринимает дату после создания — это согласованное решение). Чтобы редактор не вводился в заблуждение, в будущем поле можно сделать в режиме редактирования только для чтения, оставив возможность ввода только при создании номера. На текущий релиз — не блокирует.

3. Если редактор заполняет в статье список литературы только на русском, оставив английскую часть пустой, бэкенд отвергает сохранение с ошибкой. Поведение согласованное (требуется парность языков), форма уже отмечает обязательность EN звёздочкой. Это просто фиксация контракта.

**Что не проверяли в этой сессии (и почему):**

- Детальная посимвольная сверка текста публичных юридических страниц с эталонным сайтом questionset.ru — длительная ручная сверка, выходит за рамки одной сессии. Структурно тексты и разделы соответствуют.
- Замена PDF выпуска и статьи на новый файл — требует второго PDF-файла из набора фикстур, оставлено на следующую сессию (отдельный фокусный smoke).
- Параллельные сессии редактирования и сценарий с истёкшим токеном — длительные сценарии, не входят в обычный регрессионный пробег.

**Итоговое заключение:** релиз 0.1.11 на тестовом стенде ведёт себя стабильно по всему сценарию редактирования и публичного представления. Критических и серьёзных замечаний не обнаружено. Замечания, перечисленные выше, — косметические или согласованные, релизу не препятствуют.
