## Notes / observations

### Obs-2 (regression from 2026-05-10). Маска даты отвергает невалидное при keyboard-вводе, но принимает при JS-bypass

На форме issue#12 ввод `32.13.2026` через имитацию клавиатуры (MCP `fill`) отбрасывается — поле остаётся в предыдущем валидном значении (`01.06.2026`). Сохранение проходит со старым значением. Это улучшение по сравнению с предыдущей сессией, когда такая дата принималась.

Однако через `HTMLInputElement.prototype.value.set` + `dispatchEvent('input')` фронт принимает строку `32.13.2026` и помечает поле `aria-invalid="true"`, но **видимого текстового сообщения / красной подсветки нет**. Если бы вставка из буфера обмена шла тем же путём (по событиям input напрямую), пользователь мог бы получить визуально «нормальное» поле с невалидным значением. Не блокер, оценка S4 / nit. Возможный фикс — рядом с полем добавить inline-error при `aria-invalid="true"` (тот же CSS подсветки и текст «Неверная дата»).

### Obs-1. Сырой Python-репр в toast.error при 400 (refs.ru)

При POST `/api/articles/` с пустым `references.ru` бэк ответил 400 с DRF-форматом ошибки `{"references": ["Значение в ключе ru: значение должно быть непустой строкой."]}`. Toast.error на фронте показал содержимое в виде `{'references': [ErrorDetail(string='Значение в ключе ru: значение должно быть непустой строкой.', code='invalid')]}` — то есть `repr` Python-объекта вместо человечной строки. `parseApiError` не довёл этот случай до читабельного текста. Не блокер: содержательно понятно, что не так. Уровень: S4 / nit. Возможно — добавить ветку в `parseApiError`, которая для значений типа `ErrorDetail`/«массив строк в значении словаря» вытаскивает первую строку и форматирует `«поле X: <msg>»`.
