### Допустимые статусы

- **PASS** — кейс выполнен полностью. Конечный пользовательский результат увиден руками. В графе «Доказательство» — описание физического действия и конкретный observable.
- **FAIL** — кейс выполнен, ожидание не совпало с фактом. В графе «Доказательство» — что было увидено + ссылка на пункт «Найденные баги».
- **BLOCKED** — кейс невозможно выполнить из-за внешней причины (бэк не задеплоил, доступа к сервису нет, фикстуру невозможно восстановить даже из альтернативных источников). В графе «Доказательство» — точное описание блокера и что нужно для разблокировки.
- **SKIP** — кейс осознанно пропущен **с санкции заказчика** (ссылка на сообщение / договорённость).
- **N/A** — кейс не применим (продуктовое решение отменило требование, ссылка на согласованное решение).

### Запрещённые статусы и формулировки

Эти пометки не являются PASS и не должны появляться в Coverage Log:

- ❌ `PASS-implicit` / «covered transitively через другой кейс» — каждый кейс выполняется отдельно, либо помечается SKIP с явной санкцией.
- ❌ `PASS-via-curl` (для UI-кейса) — UI-кейс требует UI-проверки. Прямые `/api/...` вызовы допустимы только в кейсах из §7.1 и Приложения A тест-плана.
- ❌ `PASS-by-design` — «реализовано в коде», «по предыдущим сессиям», «бэкендер сказал». Прошлые сессии не считаются. Состояние кода не считается. Считается только то, что увидено руками в этой сессии.
- ❌ «Возможность есть» / «кнопка присутствует» / «поле в форме» — это описание состояния UI, а не результата операции. PASS — только когда проведено действие и увиден его результат на конечной пользовательской странице (форма после reload, публичная страница, скачанный файл и т.п.).

## Self-check перед сдачей отчёта

Выполнить **до** объявления сессии завершённой. Цель — отловить любую строчку Coverage Log, у которой PASS не подкреплён физическим действием.

- [ ] Прошёлся по каждой строке Coverage Log со статусом PASS. Для каждой могу за две секунды ответить: «какой URL открыл, какую кнопку нажал, какой именно текст / файл / поле увидел в ответ».
- [ ] Все строки SKIP / BLOCKED имеют ссылку на санкцию заказчика или конкретного блокера.
- [ ] Ни одна строка не содержит запрещённых формулировок («возможность есть», «covered through», «pass-by-design», «pass-implicit»).
- [ ] Все FAIL зарегистрированы в разделе «Найденные баги» с воспроизведением и доказательствами.
- [ ] Если в сессии правились / создавались тестовые объекты — соответствующие cleanup-шаги (или явное «оставлено по staging-политике») зафиксированы.
- [ ] Если в отчёте используются формулировки «может быть», «вероятно», «реализовано в коде» — это утверждения о коде, а не о результатах. Их нужно либо превратить в PASS с доказательством, либо в SKIP с санкцией, либо удалить.
