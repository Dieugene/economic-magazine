# Тест-план: Выпуски, Рубрики, Статьи

> **Назначение.** Сквозной ручной тест-план фронтенда ВТЭ по связке Выпуски ↔ Рубрики ↔ Статьи + публичные статичные страницы. Покрывает: отображение, редактирование, статусы выпуска, двуязычность, регрессии, статичный контент, UX-уведомления. Используется как чек-лист перед релизом и при отладке тёмных мест бэк-контракта.
>
> **Уровень тестирования.** Manual UI / E2E через браузер. Прямые `/api/...` вызовы в UI-кейсах **запрещены** — иначе ошибки фронта прячутся. Допускается curl только в Приложении A (seed) или в §7.1 (диагностика бэк-фикса), и только после явного решения тестировщика.
>
> **Поддержка.** Документ обновляется при изменении контракта бэка либо при появлении нового регрессионного кейса.
>
> **Журнал прогонов.** Каждый сеанс — отдельный markdown в `sessions/` по шаблону `sessions/_TEMPLATE.md` (SBTM-style: charter → coverage log → bugs → verdict).
>
> **История ред-ий.**
>
> - **2026-05-10** — учёл изменения и требования бэклога 2026-05-09: автоподписка всех рубрик к новому номеру; удаление UI-управления рубриками; валидация PDF на бэке; фильтрация `IssueSection.articles` по issue; контракт `references` (null либо `{ru, en}`). Добавлены блоки: соответствие предпросмотр↔публика (п.1, 3, 16), правки опубликованного номера (п.2, 18), сортировки и перекрытия страниц (п.3), даты выпуска (п.8), регрессии «эюк»-навигации (п.10), удаления управления рубриками из UI (п.11), публичных статичных страниц и куки-уведомления (п.13), UX-уведомлений об успехе и ошибках CRUD.

## 1. Окружение и предусловия

| Параметр | Значение |
|---|---|
| Web | http://185.180.230.243/ (**staging**, не prod) |
| Admin | http://185.180.230.243/control/ |
| API | http://185.180.230.243/api/ (через прокси `/backend/...`) |
| Логин | см. `CLAUDE_CONTEXT.md` (раздел «Доступы») |
| Браузер | Chrome 137+, devtools открыты, вкладка Network |
| Доп. браузер для куки-теста | любой второй браузер с пустым профилем (или приватное окно) |
| Эталонные тексты | `https://questionset.ru/` — текущая прод-версия журнала, источник юр. текстов и сравнения статичных страниц |

**Предусловия:**

1. Сессия в админке активна (свежий JWT, нет 401 в network).
2. На staging — не «подчищать за собой»: БД регенерируется отдельно, тестовые данные оставляем для последующих сессий и регрессионных проверок (см. `sessions/2026-05-05-full-staging.md`).
3. Перед каждым большим прогоном — снять снимок текущего состояния `/control/issues/` (скриншот списка) и `GET /api/issues/` (json), чтобы можно было сверить «было/стало».
4. Бинарные фикстуры (PDF, обложки, fake-PDF) — в `fixtures/`. Манифест и инструкция восстановления — `fixtures/README.md`. Папка целиком в `.gitignore`, при свежем clone — восстановить по README.

**Ключевые допущения по контракту (актуально на 2026-05-09):**

- `Issue.sections_slugs: string[]` — write-only на POST/PATCH `/issues/`. **При создании нового номера бэк автоматически подписывает все существующие рубрики**; ручная подписка/отписка через UI больше не предусмотрена (бэклог п.11).
- `Issue.sections: IssueSection[]` — read-only. После фикса бэка `IssueSection.articles` отфильтрован по `issue_id` сериализуемого выпуска (см. §7.1, защитная сетка).
- Бэк отвергает POST/PATCH статьи, если `section.slug` не в `sections_slugs` целевого выпуска. После автоподписки кейс маловероятный, но защитная логика на фронте (`ensureIssueHasSection`) сохраняется (§7.3).
- Публикация `PUT /issues/{id}/update_status/` со `status: 'Published'` требует PDF выпуска **и** PDF каждой статьи.
- Поле `references` в статье: либо `null`, либо объект с обязательными ключами `ru` и `en`. Пустую строку фронт должен либо превращать в `null`, либо подставлять оба ключа (§7.6).
- Бэк валидирует PDF: только настоящие PDF принимаются; не-PDF → 400.
- Бэк не блокирует правки полей опубликованного номера (бэклог п.2): можно менять метаданные, заменять PDF, добавлять xml-ссылки и т.п. UI тоже не должен блокировать (§F8).

## 2. Сценарий насыщения тестовой базы (seed)

**Цель.** Получить состояние, в котором есть достаточная вариативность для всех кейсов: разные статусы, статьи с разной полнотой полей, статья с большой аннотацией, статьи с разными `pages` (для сортировки), и опционально — с перекрытием диапазонов и спецсимволами.

> Управления рубриками в UI больше нет. Рубрики — фиксированный справочник; новые номера автоматически подписаны на все рубрики справочника. Создавать «QA-empty» или «QA-cross» рубрику не нужно.

### Целевая форма базы

**Выпуски (`/issues/`):**

| Маркер | Год / № / сквозной № | Статус | PDF выпуска | Дата выпуска | Назначение |
|---|---|---|---|---|---|
| QA-DRAFT | 2026 / 90 / 90 | Draft | нет | 2026-04-01 | дата выпуска, эюк-навигация |
| QA-READY | 2026 / 91 / 91 | Ready | да | 2026-04-15 | переходы статусов, предпросмотр |
| QA-PUBLISHED | 2026 / 92 / 92 | Published | да | 2026-05-01 | правки опубликованного, публичный вид |

**Статьи (минимум 7, оптимум 10):**

| Маркер | Выпуск | Рубрика | PDF | pages | Особенность |
|---|---|---|---|---|---|
| QA-A1 | QA-READY | Экон. теория | да | 1-30 | **большая аннотация (≥ 5000 символов RU)**, полный набор полей, для §F7 |
| QA-A2 | QA-READY | Экон. теория | да | 31-50 | без EN-аннотации (fallback) |
| QA-A3 | QA-READY | Методология | да | 51-72 | минимум полей, для сортировки |
| QA-A4 | QA-PUBLISHED | Экон. теория | да | 1-25 | 2 автора, 2 affiliation |
| QA-A5 | QA-PUBLISHED | Экон. теория | да | 26-44 | длинный список references (≥10) |
| QA-A6 | QA-PUBLISHED | Методология | да | 45-60 | для §F8 — заменить PDF/описание после публикации |
| QA-A7 | QA-DRAFT | любая | нет | 1-15 | для §7.5 — «эюк»-навигация |
| QA-A8 *(опц.)* | QA-PUBLISHED | Экон. теория | да | 20-35 | **перекрытие** pages с QA-A4 (1-25) и QA-A5 (26-44), для §F9 |
| QA-A9 *(опц.)* | QA-READY | Методология | да | 73-95 | спецсимволы и длинный title (≥250) |

### Порядок наполнения (через UI)

- [ ] **Шаг 1.** `/control/issues/` → «Создать номер»: QA-DRAFT (90), QA-READY (91), QA-PUBLISHED (92). Проставить даты выпусков из таблицы (если поле не редактируется — фиксируем дефект по §F10).
- [ ] **Шаг 2.** Открыть форму каждого нового номера, убедиться, что **все рубрики справочника уже подписаны** автоматически (галки стоят) — см. §F1.
- [ ] **Шаг 3.** Загрузить PDF выпусков для QA-READY и QA-PUBLISHED.
- [ ] **Шаг 4.** Создать статьи QA-A1…QA-A7 через «Добавить статью» из формы выпуска. Для QA-A1 — `abstract.ru` ≥ 5000 символов (любой связный текст: можно склеить «Lorem ipsum × N» или взять реальную аннотацию).
- [ ] **Шаг 5.** Загрузить PDF для всех статей, кроме QA-A7.
- [ ] **Шаг 6.** Перевести QA-READY → Ready, QA-PUBLISHED → Published. Если бэк отказывает — зафиксировать причину.
- [ ] **Шаг 7 (опц.).** Создать QA-A8/A9/A10 для расширенного покрытия §F9, §8.1, §7.6.

> Альтернатива через curl — см. Приложение A. Использовать только при ручном seed «с нуля», но не для замены кликов в UI-кейсах.

## 4. Smoke-сценарии

### S1. Список выпусков отображается корректно

**Шаги:** открыть `/control/issues/`.
**Ожидание:**

- Все три QA-выпуска присутствуют.
- Колонка «Статей» = фактическому числу статей **именно этого выпуска** (см. §7.1).
- Колонка «Рубрик» = `issue.sections.length` (после автоподписки — длина справочника).
- Бейджи статусов: серый (Draft), медный (Ready), зелёный (Published).
- Дата выпуска отображается в формате DD.MM.YYYY (или согласованном) и совпадает с введённой при seed.

### S2. Форма выпуска: статьи и рубрики

**Шаги:** открыть `/control/issues/{QA-READY.id}/`.
**Ожидание:**

- Чек-боксы рубрик отмечены **по всем рубрикам справочника** (после автоподписки).
- Список «Статьи номера» содержит только статьи этого выпуска, отсортирован по `pages` по возрастанию (см. §F9).
- В каждой строке — title.ru, страницы, бейдж рубрики, иконки PDF/edit/delete.
- Поле «Дата выпуска» содержит проставленную дату и доступно к редактированию (§F10).

### S3. Публичная страница выпуска

**Шаги:** `/archive/{year}/{number}/` для QA-PUBLISHED (только Published доступны публично; ID не используется в публичном URL).
**Ожидание:**

- Статьи сгруппированы по рубрикам, нигде не торчит чужая статья.
- Внутри каждой рубрики — порядок по `pages`.
- На странице выпуска присутствуют корректные дата, № номера, обложка, ссылка на PDF выпуска.

### S4. Языковой переключатель

**Шаги:** на любой публичной странице переключить RU/EN.
**Ожидание:** title/abstract/keywords обновляются на язык UI; при отсутствии перевода — fallback с пометкой `(in Russian)` / `(на английском)`.

### S5. Сайдбар админа

**Шаги:** в админке открыть боковое меню.
**Ожидание:**

- Виден пункт «Номера», работает.
- **Пункта «Рубрикатор» нет** (бэклог п.11).
- Прямой переход по `/control/sections/` — 404 или редирект на `/control/issues/` (см. §8.4).

### S6. Куки-уведомление при первом заходе (новый смоук)

**Шаги:**

1. Открыть приватное окно или пустой профиль второго браузера.
2. Перейти на корневую страницу публичного сайта.

**Ожидание:**

- В нижней части экрана появляется баннер с текстом согласия на обработку ПД и ссылкой на политику обработки ПД.
- Кнопки «Согласен» и «Не согласен».
- «Согласен» — баннер закрывается, при последующих переходах не появляется (запись в localStorage/cookie).
- «Не согласен» — редирект на `https://rkn.gov.ru/`.

## 5. Функциональные сценарии

### F1. Автоподписка всех рубрик при создании номера

**Цель.** Проверить новое поведение бэка (бэклог п.11 + комментарий разработчика).

- [ ] **Шаг 1.** `/control/issues/` → «Создать номер» с уникальным `year/number/sequential_number`.
- [ ] **Шаг 2.** Открыть форму созданного номера.
- [ ] **Шаг 3.** Сверить чек-лист рубрик с эталонным справочником (например, через `GET /api/sections/` в Network).

**Ожидание:** все рубрики справочника отмечены, без необходимости ручной подписки. Если хотя бы одна рубрика не подписана — баг бэка.

### F2. Создание статьи: авто-привязка рубрики (защитная сетка)

**Цель.** Проверить, что фронт перед POST/PATCH статьи делает `ensureIssueHasSection`, даже если бэк уже подписал всё.

- [ ] **Шаг 1.** Через curl (только для воспроизведения отрицательного состояния, бэк-инструмента в UI больше нет): `PATCH /api/issues/{QA-DRAFT.id}/` с `sections_slugs: []`.
- [ ] **Шаг 2.** В UI открыть форму выпуска QA-DRAFT, убедиться, что все галки рубрик сняты.
- [ ] **Шаг 3.** Нажать «Добавить статью», заполнить поля, выбрать любую рубрику из выпадающего списка.
- [ ] **Шаг 4.** Сохранить.
- [ ] **Шаг 5.** Вернуться на форму выпуска.

**Ожидание:** статья создана, рубрика автоматически добавилась в `sections_slugs`. В Network: PATCH `/issues/{id}/` с `sections_slugs` → 200, потом POST `/articles/` → 201. Снимок Network приложить к сессии.

### F3. Переходы статусов выпуска

- [ ] **Шаг 1.** QA-DRAFT → Ready: бэк должен принять (PDF выпуска не обязателен для Ready). Если отказывает — баг бэка.
- [ ] **Шаг 2.** QA-READY → Published: ожидание — успех, т.к. PDF и статьи на месте.
- [ ] **Шаг 3.** QA-PUBLISHED → Draft: фиксируем фактическое поведение (разрешено / запрещено).
- [ ] **Шаг 4.** На каждом успешном save — всплывашка-подтверждение (§F11).

### F4. Публикация без PDF выпуска — отрицательный

- [ ] **Шаг 1.** Создать временный выпуск QA-NOPDF (Draft, без PDF, без статей).
- [ ] **Шаг 2.** Попытаться «Опубликовать».

**Ожидание:** 400 с сообщением «В выпуске номера с ID … не загружен PDF документ». UI показывает **всплывашку** с понятным текстом ошибки (§F11), а не голый «API error: 400» в красной полосе сверху.

### F5. Публикация с PDF выпуска, но без PDF статьи — отрицательный

- [ ] **Шаг 1.** В выпуске с PDF создать статью без PDF.
- [ ] **Шаг 2.** Попытаться «Опубликовать» выпуск.

**Ожидание:** 400 с сообщением «В статье с ID … не загружен PDF документ». Всплывашка выводит этот текст с указанием на конкретную статью. См. таски `#91` (UX-индикаторы PDF + disable Publish), `#92` (Preview статьи до публикации).

### F6. Загрузка не-PDF в поле PDF (бэк-валидатор)

**Цель.** Подтвердить, что бэк-валидатор PDF (новое от 2026-05-09) работает и фронт корректно обрабатывает 400.

- [ ] **Шаг 1.** В форме статьи QA-A2 нажать «Заменить PDF», в диалоге выбора файла принудительно прокинуть `.docx` или `.txt` (через изменение `accept`-фильтра в devtools или через любой файл, переименованный в `.pdf`, но с не-PDF содержимым — fixtures/bad-not-pdf.pdf).
- [ ] **Шаг 2.** Сохранить.

**Ожидание:** бэк отвечает 400 с сообщением о невалидном PDF. Фронт показывает **всплывашку** с этим текстом. Старый PDF (если был) не затёрт, в форме осталась прежняя ссылка на файл.

## 6. Сценарии редактирования (CRUD)

> **Принцип.** Для каждого редактируемого поля: Open form → Modify → Save → Reload page → Verify the value persisted. Без reload не считается. После успешного save — всплывашка (§F11).

### E1. Выпуск: редактирование данных

| Поле | Шаги | Ожидание |
|---|---|---|
| Год | 2026 → 2025 → save → reload | значение `2025` |
| Номер в году | смена → save → reload | новое значение |
| Сквозной номер | смена → save → reload | новое значение |
| **Дата выпуска** | см. §F10 | редактируемость + paste + после reload сохранилось |
| Обложка (загруженная) | upload jpg → save | ссылка обновлена, превью корректно |
| Обложка (сгенерированная) | удалить загруженную, save | возвращается алгоритмическая (бэклог п.7 — пояснение, не баг) |
| PDF выпуска | upload pdf → save | ссылка обновлена, всплывашка об успехе |
| PDF выпуска (не-PDF) | см. §F6 | 400 + всплывашка |
| **Подписка рубрик** | бэк автоподписывает; ручное снятие галок не предусматривается UI | если в UI остались чекбоксы на форме — проверить, что снять/поставить можно (для совместимости с защитной сеткой §F2), либо что чекбоксы read-only |

### E2. Статья: редактирование всех полей

Открыть QA-A1 в `/control/articles/{id}/`. Для каждого поля по очереди: изменить → сохранить → перезагрузить страницу → проверить, что значение сохранилось. После каждого save — всплывашка об успехе (§F11a). Любая ошибка → всплывашка с понятным текстом (§F11b), а не «API error: 400 Bad Request».

- [ ] `title.ru` / `title.en`
- [ ] `abstract.ru` / `abstract.en` — отдельный кейс с текстом ≥ 5000 символов (см. §F7)
- [ ] `pages` — см. §F9
- [ ] `doi`
- [ ] `udk`
- [ ] `jel_codes` (через запятую/массив)
- [ ] `article_type` (Scientific/Review/…)
- [ ] `keywords.ru` / `keywords.en` (массив)
- [ ] `received_date`, `accepted_date`
- [ ] `funding.ru`, `funding.en` (en — условный, проверить, что пустая строка не падает с 400)
- [ ] `authors[]`: добавить, переименовать, удалить, поменять порядок (если есть кнопки), affiliations внутри автора, ORCID, email
- [ ] `references[]`: добавить, отредактировать ru/en, удалить, поменять порядок. Сохранение пустого `references` — см. §7.6.
- [ ] `section_slug`: сменить рубрику → проверить, что (а) `sections_slugs` выпуска не сломался, (б) статья «уехала» в правильную секцию на публичной странице (§F9b)
- [ ] `issue_id`: перенести статью в другой выпуск (если UI это позволяет) — проверить, что в исходном её больше нет, в целевом появилась
- [ ] PDF статьи: загрузить / заменить (валидный + не-PDF, см. §F6)
- [ ] XML/иные файлы: если поддерживаются

**Контроль:** после каждого save в Network должен быть PATCH `/articles/{id}/` → 200, тело ответа должно соответствовать новому состоянию. Если 400 — фиксируем тело ошибки и текст всплывашки.

### E3. Удаление

- [ ] Удалить статью QA-A2 → подтверждение → всплывашка «Статья удалена» → исчезла из списка выпуска.
- [ ] Удалить выпуск (тестовый, не QA-PUBLISHED) → подтверждение → всплывашка → исчез из `/control/issues/`.
- [ ] **Удаление рубрик в UI отсутствует** (бэклог п.11) — никаких кнопок «Удалить рубрику» нигде в админке.

### E4. Редактируемость в зависимости от статуса выпуска

| Статус | Что должно быть редактируемым | Что НЕ должно |
|---|---|---|
| Draft | всё (данные, статьи, обложка, PDF, дата) | — |
| Ready | то же | — |
| Published | то же (бэк не блокирует, UI не должен блокировать — бэклог п.2/п.18, см. §F8) | — |

> Любая попытка UI заблокировать поле в Published-статусе — дефект, фиксируется и возвращается на доработку.

## 7. Регрессии

### 7.1. `IssueSection.articles` содержит статьи из других выпусков (защитная сетка)

**История.** До 2026-05-09 бэкенд `IssueSection.articles` возвращал статьи глобально, без фильтра по `issue_id`. Симптомы — колонка «Статей» в `/control/issues/` показывала чужие статьи и в Published-выпусках на публичной странице отрисовывалась чужая статья. Бэкенд заявил фикс 2026-05-09.

**Защитная проверка:**

1. `GET /api/issues/{QA-DRAFT.id}/` через curl или вкладку Network (диагностика, разрешена).
2. Сверить, что для каждого `sections[i]` все элементы `sections[i].articles` имеют `issue_id == {QA-DRAFT.id}`.
3. На публичной странице `/archive/{QA-PUBLISHED.year}/{QA-PUBLISHED.number}/` — нет статей из других номеров.

**Если регрессия вернётся:** фронт страхуется фильтром `s.articles.filter(a => a.issue_id === issue.id)` в `IssueView` (см. `00_docs/specs/bug_70_issue_sections_empty.md`).

### 7.2. `abstract: null` → 400 при создании статьи

**Воспроизведение:** POST `/articles/` с `abstract: null` → 400.
**Status:** фронт всегда отправляет `{ru:"", en:""}`. Регрессия — кейс E2/«создание статьи без аннотации».

### 7.3. POST статьи с `section_slug ∉ sections_slugs` → 400

**После 2026-05-09:** редкий кейс, т.к. бэк автоподписывает все рубрики. Воспроизводится только искусственно (см. §F2).
**Ожидание:** фронт делает PATCH `/issues/{id}/` (sections_slugs) ПЕРЕД POST/PATCH статьи. Без этого — 400 + всплывашка.

### 7.4. Двуязычное соседство на странице статьи (исторический)

**Контекст:** до 2026-05-03 на `/article/[id]/` показывались RU+EN параллельно (AbstractTabs, два блока References, дублирующий title).
**Ожидание:** теперь монолингвально по `lang`, с fallback-метками. Кейс S4.

### 7.5. «Эюк»: исчезание данных при возврате со статьи в номер (бэклог п.10)

**История.** Жалоба Ореховского от 2026-04…: «выходишь со статьи в номер, возвращаешься — все заполненные данные исчезают». В сессии 2026-05-05 на v0.1.10 не воспроизвелось (фикс в коммите a09a5a8 от 2026-05-03). Держим как защитный кейс.

#### 7.5a. Сохранённая статья → возврат сохраняет данные

- [ ] **Шаг 1.** В QA-DRAFT создать новую статью QA-A7-tmp с заполненными title/abstract/keywords/pages, сохранить.
- [ ] **Шаг 2.** Из формы статьи перейти на форму выпуска (по ссылке/breadcrumbs).
- [ ] **Шаг 3.** Из формы выпуска вернуться в форму QA-A7-tmp.

**Ожидание:** все поля заполнены значениями из шага 1.

#### 7.5b. Несохранённый черновик → переход «потеряет / сохранит / предупредит»

- [ ] **Шаг 1.** В QA-A7-tmp начать менять поле, не сохранять.
- [ ] **Шаг 2.** Кликнуть по ссылке возврата на форму выпуска.

**Ожидание (целевое):** UI предупреждает «Несохранённые изменения, точно уйти?» (стандартное `beforeunload`/Modal). Если предупреждения нет, и при возврате форма пустая — это и есть оригинальный «эюк», фиксируется как дефект.

### 7.6. `references`: контракт `null` либо `{ru, en}` (комментарий бэкендера)

**История.** В отчёте 2026-05-05 был указан Bug-4 «refs RU empty causes 400». Бэкендер уточнил: поле может быть `null`; если не `null` — обязательно `{ru, en}`.

#### 7.6a. Полностью пустое references

- [ ] **Шаг 1.** Создать QA-A10 без заполнения references (или удалить все элементы у существующей статьи, сохранить).

**Ожидание:** фронт отправляет `references: null` (либо просто опускает поле в payload). Бэк → 200. Если фронт шлёт `{}` или `{ru: ""}` без `en` — 400, и это дефект фронта.

#### 7.6b. Только RU (без EN)

- [ ] **Шаг 1.** Заполнить только `references.ru`, оставить `references.en` пустым.

**Ожидание:** фронт отправляет `{ru: [...], en: []}` (массив, не строка) или согласованную форму. Бэк должен принять. Если 400 — фиксируем тело ошибки и тип несоответствия.

### 7.7. PDF-валидатор бэка (Bug-7 закрыт)

См. §F6. Регрессия — если фронт перестанет показывать всплывашку или начнёт сохранять «битый» PDF без 400.

## 8. Edge cases

### 8.1. Спецсимволы

В title статьи: `«Кавычки» — тире & «амперсанд»`, в keywords: `<тег>`, в author full_name: `O’Hara`.
**Ожидание:** сохраняются, корректно экранируются в JSX, не ломают вёрстку, не вызывают XSS.

### 8.2. Длинные строки

- title.ru ≥ 250 символов
- abstract.ru ≥ 5000 символов (см. §F7)
- references — 30 элементов

**Ожидание:** UI не «лопается», работают `truncate`/scroll, бэк принимает или возвращает осмысленную ошибку (всплывашка).

### 8.3. Контрактный provoke: рубрика не подписана к выпуску

См. §F2 (после автоподписки — синтетический кейс через curl).

### 8.4. `/control/sections/` напрямую — недоступна

- [ ] Перейти по `/control/sections/` напрямую через адресную строку.
- [ ] То же — `/control/sections/new`, `/control/sections/{slug}/`.

**Ожидание:** 404 Not Found или редирект на `/control/issues/`. Никакого UI создания/редактирования/удаления рубрик.

### 8.5. Параллельная сессия

Открыть тот же выпуск в двух вкладках, в первой сменить год → сохранить. Во второй (без reload) сменить номер → сохранить.
**Ожидание:** последний save побеждает (last-write-wins). UI не должен крашиться.

### 8.6. Истёкший JWT во время заполнения формы

- [ ] Заполнить форму большой статьи.
- [ ] Подождать, пока `vte_admin_access` протухнет.
- [ ] Нажать «Сохранить».

**Ожидание:** клиент рефрешит токен через `/auth/refresh/` и завершает запрос; форма не теряет данные. Всплывашка об успехе на следующий save.

### 8.7. Куки-уведомление: повторное появление после отказа

- [ ] **Шаг 2.** Очистить storage.
- [ ] **Шаг 3.** Снова открыть сайт.

## Приложение A. Скрипты seed через curl

> **Не пихать токен и пароли в коммиты.** Пользоваться переменными окружения. Пример для PowerShell:
>
> ```powershell
> $env:VTE_TOKEN = "Bearer eyJ..."
> $env:VTE_API = "http://185.180.230.243/api"
> ```

> **Только для seed «с нуля»** или для воспроизведения отрицательного состояния (см. §F2). В UI-кейсах прямые `/api/...` вызовы запрещены.

### A.1. Создать выпуск (рубрики бэк подпишет автоматически)

```bash
curl -X POST "$VTE_API/issues/" \
  -H "Authorization: $VTE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "year": 2026,
    "number": 91,
    "sequential_number": 91,
    "release_date": "2026-04-15"
  }'
```

> Имя поля даты выпуска (`release_date` или иное) уточнить по swagger: `http://185.180.230.243/api/schema/swagger-ui/`.

### A.2. Загрузить PDF выпуска

```bash
curl -X PATCH "$VTE_API/issues/{id}/" \
  -H "Authorization: $VTE_TOKEN" \
  -F "pdf_file=@./fixtures/issue.pdf"
```

### A.3. Создать статью (минимальный набор полей)

> Для актуального контракта `ArticleCreatePayload` см. `02_src/vte-frontend/src/lib/api/client.ts`.

```bash
curl -X POST "$VTE_API/articles/" \
  -H "Authorization: $VTE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "issue_id": 91,
    "section_slug": "ekonomicheskaja-teorija",
    "title": {"ru":"QA-A1","en":"QA-A1"},
    "abstract": {"ru":"...","en":"..."},
    "pages": "1-30",
    "doi": "10.0000/qa.a1",
    "udk": "001",
    "jel_codes": ["A14"],
    "article_type": "Scientific",
    "keywords": {"ru":["тест"],"en":["test"]},
    "received_date": "2026-05-01",
    "accepted_date": "2026-05-03",
    "funding": {"ru":"","en":""},
    "authors": [{
      "full_name": {"ru":"QA И.И.","en":"QA I.I."},
      "email": "qa@example.com",
      "orcid": "0000-0000-0000-0001",
      "affiliations": [{"organization_name":{"ru":"ИЭ РАН","en":"IE RAS"},"position":{"ru":"н.с.","en":"researcher"}}]
    }],
    "references": null
  }'
```

> Обратите внимание: `references: null` — допустимо. Если передавать объект — обязательны `ru` и `en` (см. §7.6).

### A.4. Перевести статус выпуска

```bash
curl -X PUT "$VTE_API/issues/{id}/update_status/" \
  -H "Authorization: $VTE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"status":"Published"}'
```

### A.5. Искусственно отписать рубрику от выпуска (для §F2)

```bash
curl -X PATCH "$VTE_API/issues/{id}/" \
  -H "Authorization: $VTE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"sections_slugs": []}'
```
